# Rivo Agent 集群：组建、适用场景与工作方式对比

> 核验日期：2026-09-11。本文中的“集群”指**受控网络内、经过显式配对的多个 Rivo Agent 节点协作**，不是已交付的自动调度平台。机制依据现有 A2A、Session 与节点控制实现；业务流程是使用建议，不是已经跑通的示范项目。
>
> 集群步骤须在对应环境单独验证；[发布归档验收](../runbooks/releasing.zh-CN.md)不替代跨节点互操作测试。

## 1. 先给结论：有必要再组集群

Rivo 当前最有价值的跨节点协作，是**把有明确边界的任务交给具备对应数据、权限或工具环境的节点**，再由协调者核对结果。价值首先是环境分工，其次才可能是并行提速。

不应为了“多个 Agent”而增加节点：

- 一个知识库、一项简短问答：一个 Agent + 受控检索通常更直接。
- 一个小仓库、一个工具链、一个缺陷：单开发节点通常更容易修改和验证。
- 多个独立数据域、不同发行版或不可共置的工具环境：更值得考虑节点分工。
- 任务高度串行、必须共享大量上下文、没人负责审批与汇总：集群往往增加成本。

**本地子代理、多个 MCP 数据源、现有 CI 与 A2A 集群是不同选择，不能把集群当成默认最优解。**

## 2. 当前“集群协调”实际提供什么

| 能力 | 当前可依赖的机制 | 不能据此推断 |
| --- | --- | --- |
| 节点发现与信任 | 发现候选、显式 endpoint、双端配对、固定身份与 skill grant | 自动发现后即可使用、开放注册中心 |
| 节点职责 | 本机 ServiceProfile 固定工作区、任务模式、policy、MCP 和预算 | 调用者任意改远端模型、目录、工具或权限 |
| 跨节点委派 | Client 向已选/受信任 peer 发送受限 text/json 任务 | 分布式 DAG、全局任务队列、自动负载均衡 |
| 过程与结果 | A2A Task、查询、SSE、取消和受限结果 | 完整远端会话、原始工具日志或任意文件下载 |
| 故障处理 | 已有 Task 的查询/订阅恢复，信任变化暂停，撤销 | 自动换节点、自动重演副作用或高可用续跑 |
| 节点管理 | 独立 `process-control` skill 与受控 instance-control | 全权远程 Shell、中心监督工作台 |
| 汇总 | 协调者把已收到的有效结果交给 Agent 整理，并人工复核 | 自动证明结论、自动合并代码或自动发布报告 |

### 三个容易误解的地方

1. **根 Agent 的普通工具调用按序执行。** 选择多个 peer 不等于内置“同时派发并等待全部完成”。任务是否在节点间重叠执行，要看实际提交、返回与运行时序，不能凭节点数承诺加速。
2. **A2A 入站任务不会继续创建子代理或继承本机 A2A peer 再委派。** 当前不应设计递归扩散的 Agent 网络。
3. **单节点能接收多个 Task，不等于集群有全局资源调度。** ServiceProfile 默认每 peer 一个活动任务、每 profile 三个；共享机器、Provider 和数据库的总配额仍需协调。

直接依据：[Agent 的 A2aDelegateTool 与顺序工具循环](../../runtime/crates/agent/src/lib.rs)、[A2A 入站驱动](../../runtime/crates/cli/src/main.rs)、[ServiceProfile](../../runtime/crates/a2a-server/src/lib.rs)。本仓库不再交付 FEAT-024 中心监督服务；其文档仅为未来设计参考，不承诺 V2 实现，也不是当前集群的控制面。

## 3. 建议从什么拓扑开始

**先一个协调端加一个执行节点，验证确有价值后再加第二个执行节点。** 角色是职责，不要求每个角色都单独占一台机器；需要隔离权限、工具链或资源时才拆分。

```text
用户 / 任务负责人
        │
协调端 Rivo Client
        ├── A2A → 节点 A：知识/环境只读研究
        ├── A2A → 节点 B：数据与报告生成
        └── A2A → 节点 C：指定 Linux 工具链的开发/验证
```

图中的三类节点是按实际任务负载选择的可选角色，不是要求一次部署齐全。T2/T3 的写入、构建与发布仍需节点所有者的本机审批。

协调端负责问题拆分、选择允许使用的 peer、数据最小化、记录 Task 和最终核对；执行节点负责自己的环境、工具、数据授权、预算和结果。不存在一个自动拥有全部节点权限的“集群管理员 Agent”。

Linux 节点须单独核验发行版、架构、工具链与凭据后端。发布目标包含 Linux amd64/arm64，但构件 smoke 不证明所有发行版或跨节点部署均已验证。

## 4. 如何组建一个最小协作环境

本节是组建顺序。Server 配置格式、身份准备与详细命令复用[跨平台研究集群组建手册](../runbooks/a2a-cross-platform-cluster.zh-CN.md)和[发现与配对手册](../runbooks/a2a-lan-pairing.zh-CN.md)，不要把测试身份 provisioning 当成无人维护的正式凭据方案。

### 4.1 先列职责与准备环境

在启动前人工确定：

| 项目 | 要确定的内容 |
| --- | --- |
| 任务边界 | 节点接受什么任务、拒绝什么任务；先只读研究，再评估 coding |
| 运行环境 | 已验证候选、固定工作区、模型 Provider、必要 MCP/工具链 |
| 身份与网络 | 明确私网地址、mTLS 身份、配对负责人和允许的 Client |
| 数据范围 | 可以外发的输入、可以返回的结论、禁止携带的凭据与私有材料 |
| 资源上限 | 活动 Task、工具资源、输出大小、超时及共享 Provider 额度 |
| 审批与交付 | 谁在节点本机审批、谁验收结果、文件通过哪个已批准系统交付 |

不为了方便绑定公网或通配地址，不共享整台机器的工作区，不把密钥写入任务正文。

### 4.2 启动、配对、确认技能

以下是命令模板，尖括号是需要替换的值，不是可直接复制的有效配置。先完成手册中的身份和 profile 配置；此处不自动创建证书或网络规则。

```powershell
# 执行节点：显式启动预配置服务。
rivo a2a serve <server-profile> --config <owner-a2a-server.toml>

# 协调端：发现候选，或使用经核验的显式 endpoint 配对。
rivo a2a discover
rivo a2a pair <local-identity-label> --endpoint <private-https-endpoint> --spki-sha256 <verified-fingerprint>

# 执行节点：本机负责人核对 SAS、指纹和请求后批准。
rivo a2a pairings list --config <owner-a2a-server.toml>
rivo a2a pairings approve <request-id> --config <owner-a2a-server.toml>

# 协调端：后续使用配对返回的 peer ID，而不是显示名称。
rivo a2a peers
rivo a2a inspect <peer-id>
```

配对后还须按手册核对 profile 的 `allowed_peers` 与技能授权，并使配置生效。配对成功本身不是业务任务成功，也不证明节点拥有你期望的数据或工具。

### 4.3 先做一个可核查的只读任务

例如，要求节点读取本机**事先准备、已允许访问**的项目资料，返回三个可定位结论和未知项：

```powershell
rivo run --profile research --policy medium --a2a-peer <peer-id> --prompt "请把已批准的只读研究任务委派给指定节点，要求返回结论、来源定位和未知项。未收到有效终态与结果时，不要声称任务完成。"
```

协调端 medium 用于保留跨 peer 外发确认；执行节点可保持 research/strict。二者是不同 policy 边界，不能把协调端的批准视为节点副作用授权。

`--a2a-peer` 只让模型看到允许的对端，不保证模型必然发起委派。确认实际产生了对应 A2A 请求/Task；若未发生，不把一份本地回答当作跨节点结果。

确定性指定 peer/skill 时，现有 CLI 另有 `rivo a2a delegate <peer-id> <skill-id> --message-stdin --yes [--stream]`。正文经 stdin 传入，`--yes` 是对外发的显式确认，不是节点写入审批。**当前该命令主要输出 Task ID、状态与 revision，并不是自动导出完整业务报告的命令。**

### 4.4 验证故障后再加节点

至少验证一次拒绝、取消和断线查询：

```powershell
rivo a2a recover <peer-id> <task-id>
rivo a2a cancel <peer-id> <task-id> --yes
```

仅恢复已落在当前 Client 本机存储中的 Task 映射；未知提交结果时先核查，不重新委派。不要复制其他 Client 的映射或凭据来强行恢复。

节点退出或取消不意味着已写文件自动回滚。正式使用前，应约定如何识别和处理部分产物、已完成写入及未发布结果。

## 5. 如何协调一项实际工作

### 5.1 先拆交付物，再拆节点

为每个子任务准备一份简短“任务说明”，至少包含：

- 目标与明确的非目标。
- 输入版本：资料日期、数据快照、代码 commit 或环境版本。
- 允许使用的数据与工具，以及禁止修改/发布的对象。
- 预期输出：结论、证据定位、未知项、验证命令/结果或文档引用。
- 完成条件、预算/时限、负责人和失败后的处理方式。

这是一份业务约定，不是新增的 A2A schema 字段。不要把路径、Credential、完整历史、未获准原始数据或私有记忆作为默认共享上下文。

### 5.2 当前推荐的协调流程

1. **人工或根 Agent 提出拆分方案，人确认边界。**
2. **按节点已声明技能分发独立任务。** 简单任务可以串行分发，先验证正确性；确需并行时，必须有独立提交与可观察的任务时序，不假定已有全局调度。
3. **记录 peer、Task ID、输入版本与负责人。** 业务层汇总记录应由调用方维护，不从跨节点数据库拼接或修改 runtime 内部记录。
4. **分别观察终态与交付物。** `COMPLETED` 还须伴随可读取、符合任务要求的结果，不能只看 Task ID 或“已接受”。
5. **验证版本与证据，再汇总。** 结果有冲突时回到来源核查，不用“多数 Agent 同意”代替证据。
6. **最终写入、代码集成或文档发布由一个明确负责人完成。** 其他节点返回独立结果，避免多个节点同时覆盖同一对象。

### 5.3 结果获取有实际限制

- 协调 Agent 的委派工具可以把受限 A2A 响应提供给模型，但响应可能仍是非终态 Task；必须检查状态与实际内容。
- 已对接的 A2A Client 可以通过协议查询/订阅自己的 Task；`delegate/recover` 等 CLI 状态摘要不能视为已经下载了完整报告。
- 大报告、二进制、代码仓库或构建包不是当前 A2A 任意传输能力。需要文件交付时，由节点负责人通过已批准的文档存储/代码仓库/产物系统提供带版本和访问控制的引用。
- 若尚未具备合规结果读取或文件交付路径，就先保留人工收集步骤，并将该闭环记为未自动化；不要编造“已自动汇总”的体验。

## 6. 三类场景：集群与不使用集群怎样做

### 6.1 知识库查询与对话

**任务例子**：回答一个问题，需要产品规范和运行环境两类资料。

| 不使用集群 | 使用集群 |
| --- | --- |
| 一个 Agent 通过已配置 MCP 查询两个获授权的数据源，核对来源后回答。 | 协调者把“规范核验”交给资料节点，把“环境事实核验”交给具备该环境访问权的节点，收回摘要、版本和来源后综合回答。 |
| 配置少、上下文连续、少一次拆分和汇总。 | 数据/工具权限可留在各自环境，只外发所需输入和获准的有限结果。 |

**建议**：如果两个数据源已有安全、稳定的只读接口，单 Agent + MCP 通常足够。只有数据不能集中访问、需要本机环境核验，或任务确实可独立完成时，再使用 A2A。集群不会自动提高检索质量，也不会消除进入外部模型 API 的数据风险。

### 6.2 Linux 环境数据与报告/报表

**任务例子**：生成一份同时包含业务统计和运行环境指标的报告。

可采用：

```text
业务数据节点 → 统计摘要 + 数据时间/口径 ──┐
                                       ├→ 核对一致性 → 单一报告生成/发布负责人
环境节点     → 环境指标 + 采集时间 ──────┘
```

| 不使用集群 | 使用集群 |
| --- | --- |
| 一个 T2 节点顺序读取所有允许的数据，生成、校验并发布报告。 | 两个节点在各自授权环境采集/分析，协调者核对数据日期和口径，再交由一个具备工具和存储权限的节点生成/发布。 |
| 凭据与依赖集中，流程简单，较容易保持同一数据口径。 | 避免一个节点持有所有环境权限，但增加跨节点数据一致性、结果交付与审批成本。 |

**操作要点**：

1. 固定同一统计周期或可比较的快照，不声称跨数据源具有分布式事务。
2. 节点返回聚合结果和来源，不默认搬运整库数据。
3. 先验证结果可合并，再生成文档；文档生成和远端发布是独立副作用。
4. 只设一个最终发布负责人，使用文档版本与冲突检测；发布失败不得报告为全任务成功。

**建议**：资料量小、权限可集中时，单 T2 节点更简单。报告生成很重时，应考虑将重转换独立处理，而不是给每个资料来源配置一个 Agent。文档转换工具与文件格式需按节点实际环境验证。

### 6.3 不同 Linux 发行版的代码开发与验证

**任务例子**：一个修复需要在两类明确版本的 Linux 环境验证。

```text
一个开发负责人完成候选修改并固定 commit
              ├→ 环境 A 节点：构建/测试 → 结果与版本
              └→ 环境 B 节点：构建/测试 → 结果与版本
                       ↓
              核对差异 → 修改负责人处理问题 → 重新验证 → 人工集成
```

| 不使用集群 | 使用集群 |
| --- | --- |
| 在单机 VM/受控环境或已有 CI 中切换发行版运行固定命令；一个 Agent解释失败并修复。 | 各节点维护固定发行版/工具链，节点 owner 准备同一 commit，各自执行受控验证并解释环境相关失败。 |
| 对固定构建矩阵，现有 CI 往往更可重复、更低成本。 | 对依赖特定设备、环境权限或需要探索式诊断的任务，独立 Agent 节点更有价值。 |

**操作要点**：

- 先保持“一个节点改代码，其他节点验证”，不要一开始让多个 Agent 同改同一分支/工作区。
- 代码准备与产物交换通过经批准的 Git/产物流程完成；A2A 不自动同步仓库、安装工具链或传输二进制。
- 任务输入明确 commit、工具链、已有测试命令和禁止操作；节点 owner 审批文件/进程副作用。
- 返回实际验证环境、执行结果、失败与未覆盖项；不同源码版本的通过结果不能汇总为一个候选通过。
- 自动合并、回滚、全局调度不是当前集群提供的机制。

**建议**：只需执行固定命令矩阵时优先 CI。需要节点自主分析环境相关问题时，可让 A2A 补充诊断，但不要替代最终确定性的构建与测试。

## 7. 总体对比：收益与代价都要算

| 维度 | 单 Agent / 单环境 | 受控多节点协作 |
| --- | --- | --- |
| 初始准备 | 一个环境与一组受控连接 | 每个节点都要配置、配对、授权、维护版本与审批 |
| 上下文 | 集中，连续性较好 | 只传最小任务摘要，可能丢失背景，需要明确交付约定 |
| 数据与工具 | 集中或通过 MCP 访问 | 可分置在特定环境，但结果外流与用户授权仍要管理 |
| 时延 | 串行任务简单可预测 | 只有独立任务真正重叠执行且开销较小时才可能更快 |
| 模型成本 | 较少重复规划与汇总 | 拆分、节点推理、结果复核都可能增加 token 与请求 |
| 故障 | 排查路径较短 | 增加网络、身份、版本、部分完成及跨节点结果问题 |
| 正确性 | 依赖来源和测试 | 多 Agent 可能重复同一种错误，不提供多数表决式正确性保证 |
| 扩展 | 单环境工具与资源受限 | 可增专用环境，但当前没有自动均衡/全局资源保证 |
| 责任 | 一个任务负责人较清楚 | 必须明确节点 owner、审批人、最终集成人与发布人 |

只有实际实现并验证了任务重叠执行，才可粗略比较：

```text
单节点耗时 ≈ 各子任务执行时间之和 + 最终验证/汇总
集群耗时   ≈ 拆分与分发 + 关键依赖路径耗时
           + 结果收集/核对/汇总 + 审批等待 + 故障处理
```

如果仍是串行委派，关键路径不会因节点变多自动缩短；如果共用同一 Provider 配额、数据库或文档存储，瓶颈还可能完全不在 Agent 节点。

## 8. 失败时怎样处理才可靠

| 情况 | 务实处理 |
| --- | --- |
| 只看到 Task ID，没看到业务结果 | 继续核查状态与获准的结果读取方式，不写“已完成报告”。 |
| 网络断开、提交结果未知 | 核对本机映射并查询已有 Task；不能直接重发到另一节点。 |
| 节点重启、任务失败 | 先确认已产生哪些副作用，再决定是否由人批准新任务；不承诺自动续跑。 |
| 某节点超时，其他节点完成 | 保留已验证成果，最终交付注明缺项；不使用推测补齐缺失数据。 |
| 多节点结论冲突 | 检查数据时间、代码版本、查询口径和证据，不按回答数量投票。 |
| 节点要求本机审批但无人处理 | 等待、超时拒绝或取消；不能转交协调端绕过审批。 |
| Card/证书/技能变化 | 暂停信任并重新核验，不能按相同 IP 或名称自动信任。 |
| 文件或文档部分发布 | 核查目标版本、冲突和既有结果，再由负责人处理；不盲目覆盖或删除。 |

取消协调端会话不应被假定为撤销所有远端已完成副作用。业务负责人需要核对每个远端 Task 的实际终态及交付物。

## 9. 小规模试用如何判断值不值得继续

选择一项真实、低风险、可复现的任务，先记录单节点基线，再用最少节点完成同一任务。保留相同输入版本、模型配置、工具链和完成条件，不用模型、数据或缓存差异制造加速结论。

至少记录：

- 端到端完成时间，以及拆分、模型等待、工具、审批和汇总分别耗时。
- 总模型调用/token，节点峰值 CPU/进程树内存和共享后端限流。
- 最终成果的可核查证据、验证覆盖、遗漏与人工返工。
- 配对、维护、结果收集和故障处理的人工时间。
- 在一次拒绝、取消或断线情况下，是否仍能说明每个任务发生了什么。

若集群只是让流程更长、结果更难核对，退回单节点是合理选择。若确实解决了环境隔离或专用工具访问问题，即使没有提速，也可以有价值；应明确记录价值来自哪里。

当前没有本轮集群性能或业务试用证据，不作“提升几倍效率”“自动扩容”“零人工协作”的宣传。

## 10. 下一步建议与阅读入口

1. 先完成发布归档的本机验收及最小双节点互操作，再扩大节点规模。
2. 从“一个协调端 + 一个只读节点”验证配对、任务与结果，补齐拒绝/取消/恢复。
3. 按真实业务再增加第二个节点，优先环境分工，不优先增加 Agent 数量。
4. 先把输入/输出、负责人和结果交付做清楚，再讨论自动协调。全局调度、多租户、中心监督或持久工作流仍需另行立项并遵守冻结范围。
